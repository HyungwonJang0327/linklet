## `pnpm db:migrate` 래퍼 + CLI 접속 문자열 가드 (브랜치 `chore/db-migrate-wrapper`)

- migrator(구현·실측), 메인(설계·검토·커밋·기록)

### 논의 내용
- 메인 설계: 로컬 판정 모듈 하나를 `prisma.config.ts`·래퍼·`vitest.setup.ts`·(다음) 시드가 공유. 래퍼는 우회 없음, `prisma.config.ts` 는 셸 `LINKLET_ALLOW_REMOTE_DB=1` 만 우회(M3 운영 적용은 사용자 직접)
- migrator 실측(Prisma 7.10 소스·CLI, Node 24.21): Node 24 는 `.ts` 직접 실행 가능하나 `"type"` 없는 패키지라 경고 → `.mts` 사용, 확장자 import 필수(`allowImportingTsExtensions`) / `migrate dev` 는 superuser 라 섀도 DB 자동, **`migrate diff --to-migrations` 는 `shadowDatabaseUrl` 필수·자동 생성 없음·플래그도 없음** → 래퍼가 임시 `linklet_shadow_{ts}` DB 를 CREATE/DROP / 빈 migrations 폴더에선 `--to-migrations` 실패(`migration_lock.toml` 없음) → `--to-empty` / `migrate resolve --rolled-back` 은 실패 상태 전용 → 적용 완료 마이그레이션 롤백은 down.sql 실행 + `_prisma_migrations` 행 삭제(M2 문구 수정)
- migrator 가 설계와 달리 한 것(메인 수용): 비로컬이면 무조건 throw 하면 Vercel·CI 의 `postinstall: prisma generate` 가 운영 env 와 함께 돌 때 빌드가 깨짐 → DB 없는 명령(generate·validate·format·version·init·debug)만 가드 생략, 나머지는 fail-closed. `LINKLET_ALLOW_REMOTE_DB` 는 .env 파일 값 무시(영구 우회 방지)
- 검증: 임시 `model Scratch` 로 `db:migrate` 2회(`--to-empty` 경로, `--to-migrations` + 임시 섀도 경로) → down.sql 역순 실행 → `migrate deploy` 재적용 → `--create-only` 자리표시자·pending 확인. 끝나고 임시 모델·마이그레이션 4개·`migration_lock.toml` 삭제, `db:down:clean`. 가짜 원격 문자열로 가드 거부·메시지에 값 0건 확인
