# 리뉴얼 전략

## 결정

**B. 병행 재구축** — 같은 리포의 `v2/` 디렉터리에 새 스택·새 구조로 앱을 세우고, `audit/FEATURES.md` 순서대로 기능을 한 행씩 이식한 뒤, 모든 행이 동등성 확인을 통과하면 루트로 교체한다.

운영 방식
- 새 앱 위치: `v2/` (독립 package.json·lock)
- 브랜치: main 에서 짧은 기능 브랜치 → PR 병합. 장수 renewal 브랜치는 두지 않는다
- 기존 앱(루트)은 교체 전까지 그대로 운영 배포된다. `v2/` 작업은 운영에 영향 없음
- 루트 `tsconfig.json`·ESLint 가 `v2/` 를 검사하지 않도록 제외하는 최소 수정만 기존 코드에 가한다 (Phase 0)
- 기존 코드 제거는 교체 시점에 한 번에. 조건: FEATURES.md 유지·개선 행 전부 동등성 확인 통과
- 교체 = `v2/` 내용을 루트로 올리고 기존 코드 삭제. Vercel 프리뷰 프로젝트(`v2/` 루트) 운영 여부는 환경 단계에서 결정

## 이유

| 근거 | 내용 |
|---|---|
| 부채 심각도 | AUDIT high 12개 중 다수가 구조 문제(에러 응답 6종+, PrismaClient 2개, 마이그레이션 드리프트, 에러 경계 부재, 훅 우회 fetch, 710줄 페이지) — 부분 수정보다 새 뼈대가 빠르고 깔끔 |
| 실사용자·데이터 | 실사용자 0, 데이터 폐기 가능, 다운타임 허용 — 병행 운영 부담 없음 |
| 스택 교체 폭 | Next 15→16, Prisma 6→7, 인증 라이브러리 교체, 검증 라이브러리 추가 — 제자리 업그레이드 시 장기간 전체가 깨진 상태 |
| 살릴 모듈 비율 | 메타데이터 파싱·S3·인증 헬퍼·i18n JSON·UI 기초 일부, 코드량 약 15~20%(추정) — 대부분 신규 작성 + 일부 이식 |
| 동등성 검증 | 기존 앱이 교체 직전까지 살아 있어 로컬에서 나란히 띄워 비교 가능 (완료 기준 1) |
| 포트폴리오 | `pre-renewal` 태그부터 교체 커밋까지 한 리포에 이력이 이어져 전후 비교가 쉬움 (완료 기준 9) |
| 사용자 경험 | 사용자가 이전 회사 리뉴얼에서 같은 방식을 운영해 본 경험이 있음 |

## 기각된 대안

- **A. 제자리 점진 개편** — 기존 구조를 끌고 가며 고쳐야 하고, 메이저 업그레이드 3개 + 인증 교체를 한 앱에서 동시에 하면 장기간 앱 전체가 불안정. 기존/신규 동작을 나란히 비교할 수 없음
- **C. 새 리포 재작성** — 가장 깨끗하지만 git 이력 단절, 전후 비교가 두 리포에 분산, audit/ 문서·Vercel 연결 이전 필요. 기술 위험은 낮으나 포트폴리오 서사가 약해짐

## 안전장치

- `pre-renewal` 태그: `eac797e` (0단계에서 생성, 원격 push 완료)
- 기존 코드는 새 구현이 같은 동작을 테스트로 증명하기 전까지 지우지 않는다
- 실데이터 없음(사용자 확인) → 데이터 이전 스크립트 불필요. 대신 개발·테스트용 시드 스크립트를 새로 만든다. 스키마 변경마다 되돌리기(down) 경로는 유지한다

## 확장 지점

새 기능은 `v2/` 에서만 추가한다. 이식 대상은 `audit/FEATURES.md` 에 행을 추가하는 것으로 시작하며, 교체 조건은 그 표의 상태 열로만 판정한다.
