# 앱 스킨 (사용자가 고르는 앱 화면 팔레트)

## 결정

내가 쓰는 앱 화면(목록·상세·설정 등 `(app)` 구간)에 **스킨 선택**을 넣는다. F29 화면 설정을 "테마(라이트·다크·시스템) + 언어"에서 **"스킨 + 모드 + 언어"**로 확장한다.

| 항목 | 결정 |
|---|---|
| 스킨 | 팔레트 묶음. **색·반경·그림자 토큰만** 바꾼다. 레이아웃·밀도·타이포 단계는 모든 스킨이 같다 (UX 원칙 "일관된 시스템") |
| 모드 | 라이트·다크·시스템. 스킨과 독립 — 모든 스킨은 라이트·다크 쌍을 가진다 |
| 기본 스킨 | B 깨끗한 캔버스 (`decisions/design-direction.md`) |
| 출시 스킨 | **3종** — `canvas`(기본) · `paper`(A 팔레트) · `pop`(C 팔레트, 노랑 제외). 값은 `design-tokens.md` |
| 적용 범위 | 로그인한 사용자의 앱 화면. **공유 페이지는 제외** — 공유 페이지의 모습은 소유자가 고른 프리셋(F27)이 결정하고, 보는 사람의 앱 스킨은 영향을 주지 않는다 |
| 저장 | 사용자 설정으로 서버 저장(F29 "새로고침 후 유지"와 같은 경로). 값은 영어 코드(`'canvas'`, `'paper'`, `'pop'`) |
| 구현 방식 | 스킨 = CSS 변수 집합 교체(`data-skin` + `data-mode` 속성). 컴포넌트는 토큰만 쓰므로 스킨 추가 시 컴포넌트 수정 없음 |

## 이유

- 사용자 요청 (2026-11-08): "유저가 테마를 설정할 수 있는 기능 — 스킨 갈아끼우듯이"
- 시각 방향 B의 장점이 "토큰이 적고 라이트·다크 구조가 같다"는 점이라, 팔레트 교체 비용이 가장 낮은 안 위에 스킨을 얹는 것은 결정과 일관된다
- A·C 시안의 팔레트는 이미 라이트·다크 대비 검증(4.5:1)을 통과했으므로 스킨 후보로 재사용하면 추가 디자인 비용이 거의 없다
- 스킨을 색·반경·그림자로 한정하는 이유: 레이아웃까지 바꾸면 화면마다 스킨 수만큼 검증해야 하고, 접근성 기준선(대비·포커스)을 스킨마다 다시 봐야 하는 범위가 커진다
- 공유 페이지를 제외하는 이유: 공유 페이지는 소유자의 "꾸미기" 결과물이고(F27), 보는 사람의 설정이 섞이면 소유자가 의도한 모습이 깨진다

## 기각된 대안

- **스킨 없이 라이트·다크만** (기존 F29) — 사용자 요청 미충족
- **스킨이 밝음·어두움을 포함** (모드 선택 제거) — 설정이 하나로 줄지만 시스템 다크 자동 추종이 불가능하고, 스킨마다 다크 변형을 따로 만들어야 해 스킨 수가 두 배가 된다
- **앱 스킨과 공유 페이지 프리셋을 하나의 목록으로 통합** — 토큰 체계는 단순해지지만 F27 프리셋 6종 정의를 다시 잡아야 하고, 프리셋은 "남에게 보여주는" 용도라 요구(배경 이미지·강조색 1개 등)가 다르다. 토큰 이름은 공유하되 목록은 분리한다
- **스킨이 레이아웃·타이포까지 변경** — "일관된 시스템" 위반, 검증 범위 폭증

## 확장 지점

- 새 스킨 = 라이트·다크 변수 집합 2개 + 대비 검증표 한 줄. `design-tokens.md` 에 스킨 표를 두고 거기에 행을 추가한다
- 공유 페이지 프리셋(F27)이 같은 토큰 이름(`--c-*`)을 쓰면, 프리셋도 같은 메커니즘으로 구현할 수 있다 — F27 이식 때 판단
